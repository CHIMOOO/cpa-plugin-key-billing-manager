# State 多账号并发采集方案（2026-09-21）

状态：**设计方案，尚未实现或启用**。账号页的批量并发设置控制业务请求，不改变本方案所述的采集并发。

## 推荐规则

采用“不同账号并行，同一账号串行”：默认同时采集 **2 个账号**，管理员可设 **1–10**，改为 1 即保留现有串行效果。每个账号无论配置多少模型，都最多有一个在途请求；请求结束后保留至少 2 秒间隔、账号暂停和每桶重试规则。到期前续采优先，同时保留缺票桶的公平机会。

每个在途任务独占一条完整代理配置，不把同一条分给另一个账号。代理数不足时降低实际并发，不自动回退直连；用户未配置代理而明确使用直连时，并发维持 1。继续使用现有顺序游标，成功或失败结束后释放占用，下一个任务取后续条目。配置降低并发时，让已有请求收尾，不再补充超出新上限的任务。

例如 10 个账号、每个账号 2 个模型，每条请求约 3 秒，忽略调度间隔时总网络等待约 60 秒；2 并发约 30 秒，5 并发约 12 秒。实际耗时还受代理、2 秒间隔、预算、失败重试和上游限制影响。主要收益是一个账号等待 25 秒超时期间，其他账号可以继续。

## 代理和账号隔离的边界

- 请求只使用任务指定账号的凭据、模型和代理，不修改 CPA 的账号启用状态、全局代理或业务 `proxy_url`，不临时切换业务号池。
- 不同代理 URL、会话用户名、新 TCP 连接都**不保证不同公网出口 IP**。像 `us.1024proxy.io:3000` 这样的轮换网关可能把不同会话分配到同一个 IP；当前 TCP 连通性检测只检查入口端口，不能验证实际出口。
- 若必须为不同账号使用不同公网 IP，应准备服务商明确分配的独立固定出口，或有明确独占保证的粘性会话。并发采集器只能保证不同任务独占所分配的配置条目；多种 URL 指向同一出口时还需运营者归并出口标识，不能宣称软件凭 URL 自动保证 IP 唯一。
- 账号的上游额度、机器带宽、连接数及磁盘仍被采集与业务共同使用。因此从 2 并发开始，观测后再调高；不会承诺只要分开代理就不触发上游限制。

## 为什么不能直接增加 10 个线程

当前存在三层串行约束：

1. `internal/statecollector/collector.go` 的循环等待当前 `/runner/tick` 完成。
2. `internal/plugin/turn_state_runner.go` 用单个 `inFlight` 状态保证只有一个任务。
3. `internal/turnstate/probe.go` 的 `probeMu` 从选桶、读取凭据到网络请求结束一直持有；当前进度也只有一个槽位。

只增加 worker 会得到忙碌冲突，不能实现有用并发。也不能简单移除锁，否则会重复预留同一桶、越过预算，或把其他任务的新模板覆盖掉。

## 执行架构

优先保持 OAuth 凭据在 CPA 插件内，外置 `cpa-state-collector` 管理有界 worker 和独立心跳，每个 worker 调用一次同步插件执行请求。插件不新增后台协程或定时器。

将采集拆成三个阶段：

1. **预留**：短锁中检查采集意图、宿主账号存在性、到期时间、账号槽位、代理占用和冷却；原子持久化全局小时预算、出口尝试次数及游标，生成任务 ID。写入失败不发送请求。
2. **执行**：释放全局调度锁，按已确定的账号／模型／代理读取凭据并请求；使用独立连接、25 秒总超时，以及原有可选严格完成校验。
3. **提交**：短锁中核对任务身份与代次，仅合并该任务的结果；按真实签发时间判断新旧票，并检查丢弃指纹。禁止整份旧快照覆盖别人的模板、配置或计数。

任务至少包含 `task_id`、collector 实例、runner 代次、账号／模型、配置策略版本和开始／截止时间。任务表同时管理账号槽位及代理占用；多任务进度分别显示任务 ID、账号、模型、代理序号、阶段和耗时。

小时预算仍是所有账号、模型及代理池共用，发送前预留。失败、超时或无法确认是否发送的任务不自动退还预算。并发不取消用户设置的账号冷却、静态／轮换重试预算、模板到期检查或代理最低保留数；丢弃模板不是代理失败，不应触发代理淘汰。

## 停止、恢复和旧结果隔离

- 停止后立即禁止新预留，取消尚未发送的任务；在途请求按停止策略取消或收尾。已经发送的上游请求不可撤销。
- 停止再启动、租约接管、切换数据路径、删除账号、清空／丢弃模板后，旧代任务不得写回新状态。重复提交必须幂等。
- 采集器失联时通过独立心跳和租约恢复；仍可能执行的旧任务，在结束或安全超时之前不能释放其账号占用后立即重发。预算保持持久化记录。
- 修改代理池时，新任务使用新版本；在途任务继续使用预留快照。完成回调不能按旧数组下标误删编辑后换入的新代理。
- 有效旧票在续采期间继续使用；换票只影响后续业务请求，不重放已发送业务请求。

## 上线前验证

首先使用真实兼容版本 CPA 配合本地模拟上游，验证宿主是否允许管理接口并行执行。仓库是 CGo 动态插件，但仅有 Go race 测试不能证明宿主调用没有额外串行锁，也不能证明并发采集不影响业务 HTTP/SSE 或 WS 转 HTTP 桥接。

1. 模拟 10 个账号与不同延迟：检查总并发、单账号串行、代理独占、续采公平性、预算和游标的原子性。
2. 注入超时、断连、磁盘失败、重复结果、租约接管、账号删除、停止再启动和模板丢弃：检查不超采、不串号、不恢复旧票、不覆盖其他任务。
3. 在 CPA 上分别跑 1、2、3、10 并发，同时持续发送业务请求与管理操作：验证并发确实生效、资源与响应延迟可接受，并可随时退回 1。
4. 验证通过后才启用默认 2。若宿主实际串行化或并发调用影响业务，则另外设计由独立采集器执行网络请求的方案；这会改变“采集器不接触上游 OAuth 凭据”的边界，必须补本机凭据交付、任务结果核验和租约隔离，不能靠改 CPA 或增加线程绕过。
